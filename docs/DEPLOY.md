# 배포 구조와 규칙 (Docker Compose 기반, 초안 2026-11-08)

서버 배포를 Docker로 할 수 있도록, 지금 만드는 로컬 실행 환경과 앞으로 만들 Spring·Python·웹 코드가 **고치지 않고** 같은 Docker Compose 구조로 서버에 올라가게 하는 구조와 규칙이다(소유자 지시 2026-11-08). 이 문서가 배포의 정본이다. PLAN §10(기술 스택)·§11(로드맵)·§15(저장소 구조), SPRING_JPA §3·§9·§10은 여기를 가리킨다. MACRO_ETF §6.4는 방법론 문서의 참고 설명이며 배포는 이 문서가 우선한다.

> 이 문서는 문서와 공개 웹 문서만 읽고 썼다. Docker·DB·CI를 **실행해 확인하지 않은 부분**(CI 절차, 메모리 예산 등)은 손으로 추적·계산한 것이고, 확인하지 못한 사실은 "확인 필요"로 적었다. 한도·가격은 바뀌므로 확인 날짜를 함께 적는다(MACRO_ETF 부록 A 머리말과 같은 원칙).

**무엇을 지금 하고 무엇을 미루는가:** 지금(Phase 0)은 로컬 `compose.yaml`(서비스 `db`·`api`)과 **이름·포트·비밀값·설정 규칙**만 정한다. 이미지(Dockerfile)는 각 서비스가 생기는 단계(api는 Phase 0의 P0-24, engine은 M2, proxy는 APP)에서 만들고, 운영 배포 구성(`compose.prod.yaml`·Caddy·백업·배포 워크플로)은 OPS까지 만들지 않는다. 단계별 준비 일은 §11에 정리한다.

## 1. 원칙

1. **같은 이미지, 다른 설정.** 이미지는 한 번 빌드해 로컬·CI·운영에서 같은 것을 쓰고, 달라지는 것은 환경 변수와 비밀값뿐이다(12-factor).
2. **외부(0.0.0.0)에 열리는 포트는 `proxy`의 80·443뿐이다.** 다른 서비스의 `ports:`는 언제나 `127.0.0.1:` 접두사를 쓴다(§5).
3. **DB에 쓰는 것은 Java뿐이다**(PLAN §10)를 구조로 강제한다: 엔진(`engine`)은 내부 네트워크에만 붙고 DB는 읽기 전용 역할로 접속한다(§5, §7).
4. **이미지에 비밀값을 굽지 않는다**(§9).
5. **로그는 stdout/stderr로만** 낸다(§8).
6. 구조는 호스팅 결정과 무관하게 같다 — OCI든 다른 VM이든 Compose 구조는 그대로다(§10).

## 3. compose 파일 구조와 실행 명령

| 파일 | 추적 | 내용 | 실행 |
|---|---|---|---|
| `compose.yaml`(루트) | 예 | **로컬 기준 + 공통 정의.** Now: `db`, `api` (profile `api`), `prometheus` and `grafana` (profile `monitoring`, MON-02). / 지금은 `db`·`api`(profile `api`)·`prometheus`·`grafana`(profile `monitoring`, MON-02)가 있다. 서비스가 생길 때마다 추가한다(`engine` M2). 선택 서비스는 `profiles:`로 관리한다. 운영은 `/opt/antlab/.env`의 `COMPOSE_PROFILES=api` 또는 `compose.prod.yaml`의 `profiles: !reset []`로 항상 켠다(`!reset`의 profiles 적용은 OPS에서 **확인 필요**) | `docker compose up -d` |
| `compose.prod.yaml`(루트) | 예(OPS) | 운영 덮어쓰기: `image:`를 GHCR SHA 태그로, `build:` 제거, `db` 인증을 비밀번호(secrets)로 하고 `POSTGRES_HOST_AUTH_METHOD: scram-sha-256`을 **명시**(키를 빼면 공통 파일의 trust가 남는다 — 아래), `proxy` 추가, `restart: always`, `logging` 회전, `mem_limit`, 필요하면 `ports: !reset []` | `docker compose -f compose.yaml -f compose.prod.yaml up -d` |
| `compose.override.yaml` | **아니오**(`.gitignore`에 이미 있음) | 개인 로컬 조정(포트 바꾸기 등) — Compose가 자동 병합 | 자동 |
| `deploy/Caddyfile`, `deploy/backup/*.sh` | 예(OPS) | 프록시·백업 | — |

- 선택 이유: **공통 파일 + 운영 덮어쓰기 파일 + profiles(선택 서비스)**. 대안 — 환경마다 완전한 파일 두 개(`compose.dev.yaml`·`compose.prod.yaml`)는 중복이 커지고 서로 어긋난다. profiles만으로 dev/prod를 가르는 안은 같은 서비스의 설정(인증·포트)을 profile로 바꿀 수 없어 서비스 이름이 갈라진다(`db-dev`/`db-prod`).
- 병합 주의: `ports`는 목록이 **더해진다.** 지우려면 `!reset []`, 바꾸려면 `!override`(도입 판은 **확인 필요** — 병합 참조 페이지에 판 언급이 없다. Compose v5.1.3에서 `!reset null` 동작 확인, 2026-11-08). `docker compose config`가 `!reset`을 반영하지 않는다는 버그 보고(docker/compose #12162)가 있어 운영에서는 `docker compose ps`·`docker port`로 확인한다. 그래서 포트 원칙 자체를 "호스트 포트는 127.0.0.1에만"으로 두어 덮어쓰기 실수가 있어도 외부에 열리지 않게 한다(§5).
- **trust는 로컬·CI 일회성 전용이다.** 운영·공유 환경에서는 쓰지 않는다. 운영으로 바꿀 때 함정 셋:
  1. `environment`는 키 단위로 병합된다. `compose.prod.yaml`에 비밀번호만 더하면 공통 `compose.yaml`의 `POSTGRES_HOST_AUTH_METHOD: trust`가 병합 결과에 그대로 남는다(`docker compose -f compose.yaml -f compose.prod.yaml config`로 확인, 2026-11-08). 그래서 운영 덮어쓰기는 `POSTGRES_HOST_AUTH_METHOD: scram-sha-256`을 명시한다(키를 지우는 `!reset null`도 동작하지만 값이 보이는 쪽을 쓴다). 배포 전 확인은 `config` 출력에서 이 키를 본다.
  2. postgres 이미지의 `POSTGRES_*` 변수는 **빈 데이터 디렉터리로 처음 시작할 때만** 적용된다(Docker Hub postgres 문서). 이미 만들어진 볼륨의 `pg_hba.conf`는 변수를 바꿔도 그대로다. 운영 DB는 **새 볼륨으로 초기화**하고 로컬 볼륨을 옮겨 쓰지 않는다(데이터는 덤프·복원으로). 기존 볼륨의 인증을 바꿔야 하면 `pg_hba.conf`를 직접 고쳐 다시 읽히는 별도 절차로 한다(OPS).
  3. OPS 완료 기준에 "비밀번호 없는 TCP 접속이 거부된다" 시험을 넣는다(다른 컨테이너에서 `psql -h db …`. 컨테이너 안 유닉스 소켓 접속은 이미지 기본 설정상 비밀번호 없이 될 수 있다 — **확인 필요**).

- JVM 메모리: 컨테이너 한도(`mem_limit`)를 주고 `-XX:MaxRAMPercentage=75` 같은 비율로 쓴다(JDK가 컨테이너 한도를 인식 — 값은 OPS에서 측정 후 확정).
- 태그: `:{git 짧은 SHA}` + `:main`(최신). 운영 compose는 **SHA 태그**를 쓴다(앱 되돌리기 = 이전 SHA로 `up -d --wait`. DB 스키마는 함께 돌아가지 않는다 — §7 "되돌리기").
- 루트 `.dockerignore`(P0-24에서 만듦, Dockerfile은 `COPY . .` 없이 필요한 입력만 복사): `.env`, `.env.*`, `data/`, `db/sample/*.csv` 중 무시할 파일, `.git/`, `**/.venv/`, `node_modules/` 등. 빌드 컨텍스트에 `.env`가 들어가면 `COPY . .` 한 줄만으로도 키가 이미지에 들어간다.

- Dependency layer (M1-02, #86): the Dockerfile copies only `gradlew`, `settings.gradle`, `build.gradle` and `gradle/`, runs `./gradlew resolveDependencies` (a task in `build.gradle` that downloads the compile, runtime and annotation processor classpaths), and only then copies `src/main` and runs `bootJar --offline`. The dependency step is reused until a build file changes, and `--offline` makes a dependency the step missed fail the build instead of being downloaded. A source-only change rebuilds only the last steps (measured on the owner device, 2026-11-17: 28.7 s cold, 8.5 s with a source-only change). Job `image` of `.github/workflows/api.yml` builds the same Dockerfile on `ubuntu-24.04-arm` with buildx and the `type=gha` layer cache, `push: false`, `load: true`; there is no login step and no `packages` permission. A BuildKit cache mount was not used: `cache-to: type=gha` does not export mounts, so a fresh runner would start empty. / 의존성 레이어(M1-02, #86): Dockerfile은 `gradlew`·`settings.gradle`·`build.gradle`·`gradle/`만 먼저 복사해 `./gradlew resolveDependencies`(`build.gradle`의 작업으로 compile·runtime·annotation processor 클래스패스를 내려받는다)를 돌리고, 그다음에야 `src/main`을 복사해 `bootJar --offline`을 돌린다. 의존성 단계는 빌드 파일이 바뀔 때까지 재사용되고, `--offline` 덕분에 이 단계가 빠뜨린 의존성은 내려받지 않고 빌드를 실패시킨다. 소스만 바뀌면 마지막 단계들만 다시 돈다(소유자 기기 실측 2026-11-17: 처음부터 28.7초, 소스만 바꿨을 때 8.5초). `.github/workflows/api.yml`의 job `image`는 같은 Dockerfile을 `ubuntu-24.04-arm`에서 buildx와 `type=gha` 레이어 캐시로 `push: false`, `load: true`로 빌드하며, 로그인 단계와 `packages` 권한이 없다. ## 5. 네트워크·포트

1. **외부(0.0.0.0)에 바인딩하는 포트는 `proxy`의 80·443뿐이다.** 다른 서비스의 `ports:`는 언제나 `127.0.0.1:` 접두사를 쓴다. Docker가 공개한 포트는 호스트 방화벽(ufw 등) 규칙을 우회할 수 있다는 점이 흔한 사고 원인이다(Docker 문서 "Packet filtering and firewalls": 게시한 포트의 트래픽은 ufw 규칙보다 먼저 라우팅된다, 2026-11-08 확인) — 127.0.0.1 바인딩이면 이 문제가 생기지 않는다. Docker 28.0.0 이전 판은 같은 L2 세그먼트의 다른 호스트가 127.0.0.1 게시 포트에 닿을 수 있었다(Docker 문서 Port publishing) — 운영 VM은 Docker 28 이상을 쓴다. OCI 보안 목록(Security List)도 22·80·443만 연다.
2. 네트워크 셋: `edge`(proxy ↔ api·n8n), `backend`(api ↔ db·engine, `internal: true` — 바깥 인터넷으로 나가지 못함), `egress`(api·agent-runner의 외부 호출: KIS 시세, FRED, OpenRouter). `db`·`engine`은 `backend`에만 붙는다 → 엔진은 외부 데이터를 부를 수 없다(사후 정보 배제 PLAN §4.5를 네트워크가 한 번 더 막는다).
   `internal: true`는 **운영 덮어쓰기(`compose.prod.yaml`)에서만** 건다. internal 네트워크에만 붙은 컨테이너는 `ports:`가 있어도 호스트에 게시되지 않는다(Docker Desktop 29.5.2·Compose v5.1.3에서 시험, 2026-11-08 — 운영 Linux 엔진에서도 OPS 때 확인). 로컬 `compose.yaml`의 `backend`는 일반 브리지라 db·engine이 127.0.0.1에 열린다. 포트 게시와 외부 송신 차단은 별개 조건이므로 OPS에서 호스트→db, api→db·engine, db·engine→인터넷을 각각 시험한다.
3. 운영 DB 관리 접속은 SSH 터널 또는 `docker compose exec db psql`. DB 포트를 인터넷에 열지 않는다.
4. 엔진은 Spring만 부른다(MACRO_ETF §6.5 "Python은 내부 네트워크, 서비스 토큰"): 같은 `backend` 네트워크 + 공유 비밀 `ANTLAB_ENGINE_TOKEN`.
5. 에이전트 러너는 DB에 쓰지 않는다(PLAN §10) — `egress`로 api의 TurnView·주문 API만 부르고 `backend`에 붙지 않는다.
6. The management port `8081` is reachable from every network `api` joins (`backend`, `edge`, `egress`), because Docker cannot bind a port per network. Only `prometheus` (on `backend`) calls it; the proxy (OPS `Caddyfile`) never routes to it, and it is never listed under `ports:`. / 관리 포트 `8081`은 Docker가 네트워크별로 포트를 묶을 수 없어 `api`가 붙은 모든 네트워크(`backend`·`edge`·`egress`)에서 닿는다. 이 포트는 `backend`의 `prometheus`만 부르고, proxy(OPS `Caddyfile`)는 이 포트로 경로를 두지 않으며 `ports:`에도 넣지 않는다.
7. Internal only, never published: `postgres-exporter` 9187 (OBS-06). It has no `ports:` entry and joins `backend` only; Prometheus (on `backend`) is the only caller. / 내부 전용, 게시하지 않음: `postgres-exporter` 9187(OBS-06). `ports:`가 없고 `backend`에만 붙으며 호출하는 것은 `backend`의 Prometheus뿐이다.

## 6. 볼륨·백업·복원·메이저 업그레이드

- 이름 붙은 볼륨만: `db-data`, `caddy-data`(인증서 — 영속 필수, Caddy 문서), `caddy-config`, `n8n-data`, `ollama-models`. 바인드 마운트는 설정 파일(`Caddyfile`)만, 읽기 전용.
- 백업(OPS, 초안): **VM의 cron 하나**가 매일 밤 실행한다(compose `backup` profile은 두지 않는다 — 일정·자격 증명·실패 알림이 두 곳으로 갈라지지 않게). 스크립트는 `set -euo pipefail`로 덤프·암호화·업로드 단계마다 실패를 잡아 알린다(`job_run` + Slack, OPS).
  1. DB 덤프: `docker compose exec -T db pg_dump -U <소유 역할> -d antlab -Fc`. `pg_dump`는 **DB 하나만** 덤프하고 역할·테이블스페이스 같은 클러스터 전역 객체는 넣지 않는다(PostgreSQL 17 문서).
  2. 역할 덤프: `docker compose exec -T db pg_dumpall -U <슈퍼유저> --globals-only` — 역할(`antlab_owner`·`antlab_app`·`antlab_engine`)과 권한을 다시 만들기 위해서다. 역할 비밀번호(해시)가 기본으로 들어간다.
  3. 두 파일을 암호화(`age` 또는 `gpg` — 회원 이메일·비밀번호 해시가 들어가므로)해 OCI Object Storage(Always Free 20 GB, S3 호환 API — 업로드 도구는 OPS에서 `oci` CLI/`rclone` 중 결정)에 올린다. 보존은 7일 일간 + 4주 주간(초안).

  역할 이름·슈퍼유저 이름은 MVP의 DB 역할 결정(§7) 뒤 확정한다. 블록 볼륨 백업(무료 5개)은 VM 통째 복구용 보조다.
- **복원 시험**을 OPS 완료 기준에 넣는다: 새 볼륨의 빈 컨테이너에 ① 역할 덤프 적용(`psql`) → ② `pg_restore -d antlab` → ③ 대사 쿼리 PASS → ④ `antlab_app`·`antlab_engine`으로 비밀번호 접속, 엔진 역할의 쓰기 거부 확인 → ⑤ 그 DB로 `api`가 시작해 readiness 통과.
- **메이저 업그레이드 주의:** `postgres:18`부터 이미지의 `PGDATA`가 `/var/lib/postgresql/18/docker`, 선언 `VOLUME`이 `/var/lib/postgresql`로 바뀌었다(docker-library/postgres PR #1259, 2025-06 병합). 17 볼륨을 18 이미지에 그대로 붙이면 시작하지 않거나 빈 DB가 된다. 18로 올릴 때는 위 백업 두 파일(DB 덤프 + 역할 덤프) → 새 볼륨 → 복원(또는 `pg_upgrade`)으로 한다. 지금 17의 마운트 경로 `/var/lib/postgresql/data`는 맞다. AI 단계에 pgvector 이미지로 바꿀 때도 같은 덤프·복원 절차를 쓴다.

## 7. 마이그레이션과 DB 역할

- **선택: 앱 시작 때 Flyway**(SPRING_JPA §3 그대로). `api`가 하나뿐인 단일 VM에서는 마이그레이션 경합이 없다. 배포 스크립트는 ① `up` 전에 `pg_dump`를 한 번 뜨고(§6), ② `docker compose -f compose.yaml -f compose.prod.yaml up -d --wait --wait-timeout 180`으로 모든 서비스가 healthy가 될 때까지 기다린 뒤, ③ proxy를 거친 실제 API 요청 한 번(경로는 OPS에서 정함)이 성공해야 배포 성공으로 기록한다. `up -d`만 쓰면 컨테이너가 만들어지는 순간 성공으로 끝나 Flyway·`validate` 실패를 잡지 못한다. `--wait`는 서비스가 unhealthy이면 종료 코드 1로 끝난다(Compose v5.1.3에서 시험, 2026-11-08 — 공식 문서는 이 종료 코드를 따로 적지 않는다). 실패하면 워크플로를 실패로 끝내고 **자동으로 되돌리지 않는다** — 아래 "되돌리기"대로 소유자가 판단한다.
- **되돌리기 — 앱과 스키마는 따로다.** 이전 SHA로 `up`하면 앱만 돌아가고, 새 판이 시작하며 적용한 Flyway 마이그레이션은 DB에 그대로 남는다. ① 새 마이그레이션이 없거나 이전 앱과 호환되는 변경(테이블·열 추가, 제약 완화)뿐이면 이전 SHA로 되돌린다. ② 이전 앱이 읽지 못하는 변경(열 이름 변경·삭제, 타입 변경, 제약 강화)은 이미지 롤백으로 복구되지 않는다 — `api`를 멈춰 쓰기를 막고 배포 직전 덤프로 복원하거나(§6 복원 절차), 고친 판을 다시 배포한다(전진 수정). 그래서 비호환 변경은 두 배포로 나눈다(새 구조 추가 → 다음 배포에서 옛 구조 삭제).
- 대안: 별도 일회성 서비스 `migrate`(profile `tools`, 같은 api 이미지에 `--spring.main.web-application-type=none` 또는 `flyway/flyway` 이미지) → `docker compose run --rm migrate` 뒤 `up -d api`. 여러 인스턴스·긴 마이그레이션이 생기면 이 안으로.
- DB 역할(MVP-20에서 확정): Flyway는 소유 역할 `antlab_owner`(DDL), 앱은 `antlab_app`(DML만), 엔진은 `antlab_engine`(**SELECT만**). Spring은 `spring.flyway.user`/`password`로 마이그레이션 접속을 따로 줄 수 있다. 엔진의 읽기 전용 역할은 PLAN §10 "DB에 쓰는 것은 Java뿐"을 DB 권한으로 강제한다. MVP-20: `antlab_owner` owns schema `public` and every table and runs Flyway (`spring.flyway.user`); `antlab_app` is the app's login with SELECT/INSERT/UPDATE by table class and no DDL, DELETE or TRUNCATE; both are created by the tracked superuser script `db/roles/antlab_owner_app.sql` (no password in the repository), on a fresh compose volume automatically through `/docker-entrypoint-initdb.d`. The per-table grants are applied by the Flyway callback `db/callback/afterMigrate.sql` after every migrate, so a new table must be added to one class in the same PR. Order on a database: role script → app start → `antlab_engine.sql` → `grafana_reader.sql`. / MVP-20: `antlab_owner`는 `public` 스키마와 모든 테이블을 소유하고 Flyway를 실행한다(`spring.flyway.user`). `antlab_app`은 앱의 로그인 역할로, 테이블 분류별 SELECT·INSERT·UPDATE만 있고 DDL·DELETE·TRUNCATE는 없다. 두 역할은 추적하는 슈퍼유저 스크립트 `db/roles/antlab_owner_app.sql`이 만들고(저장소에 비밀번호 없음), 새 compose 볼륨에서는 `/docker-entrypoint-initdb.d`로 자동 실행된다. 테이블별 권한은 Flyway 콜백 `db/callback/afterMigrate.sql`이 마이그레이션마다 적용하므로 새 테이블은 같은 PR에서 분류 하나에 넣는다. DB 한 개의 순서: 역할 스크립트 → 앱 시작 → `antlab_engine.sql` → `grafana_reader.sql`.
  OBS-01: `grafana_reader` is created by the tracked, idempotent script `db/roles/grafana_reader.sql`, not by Flyway. It gets CONNECT, USAGE on schemas `obs` and `public`, SELECT on every `obs` view, and SELECT on the two public macro tables `series` and `series_observation` (nothing else in `public`). Its sessions default to read-only transactions with a statement timeout. The views are created by Flyway as `antlab_owner` (the owner script creates schema `obs`, because `antlab_owner` has no CREATE on the database) and never contain prompt or reply text, free-text error details, member credentials or season-path dates. Order on an existing database: run `db/roles/antlab_owner_app.sql` again (creates `obs`) → start the app (Flyway V13 creates the views) → run `db/roles/grafana_reader.sql`; run the reader script again after any migration that creates or recreates a view. On a new volume the owner script runs automatically, so only the reader script is run by hand. / OBS-01: `grafana_reader`는 Flyway가 아니라 추적하는 멱등 스크립트 `db/roles/grafana_reader.sql`로 만든다. 권한은 CONNECT, `obs`·`public` 스키마 USAGE, 모든 `obs` 뷰의 SELECT, 공개 거시 테이블 `series`·`series_observation`의 SELECT뿐이다(`public`의 그 밖의 것은 없다). 세션은 기본으로 읽기 전용 트랜잭션이고 문장 시간 제한이 있다. 뷰는 Flyway가 `antlab_owner`로 만들며(`antlab_owner`는 DB에 CREATE 권한이 없어 `obs` 스키마는 소유자 스크립트가 만든다) 프롬프트·응답 원문, 자유 서술 오류 내용, 회원 인증 정보, 시즌 경로의 날짜를 담지 않는다. 기존 DB의 순서: `db/roles/antlab_owner_app.sql` 다시 실행(`obs` 생성) → 앱 시작(Flyway V13이 뷰 생성) → `db/roles/grafana_reader.sql` 실행. 뷰를 만들거나 다시 만드는 마이그레이션 뒤에는 읽기 스크립트를 다시 실행한다. 새 볼륨에서는 소유자 스크립트가 자동으로 돌아 읽기 스크립트만 손으로 실행한다.
  M2-08: `antlab_app` may UPDATE only the regime columns of `month_block` (column grant in `afterMigrate.sql`); `antlab_engine` stays SELECT-only. The script needs no table, so it can run any time after the database exists (the smoke runs it after Flyway); run it after `docker compose down -v` or a new volume. Order on a database: role script → app start → `antlab_engine.sql` → `grafana_reader.sql` → `antlab_metrics.sql` (the last three are independent of each other). / OBS-06: `antlab_metrics`는 Flyway가 아니라 추적하는 멱등 스크립트 `db/roles/antlab_metrics.sql`로 만든다. 권한은 DB CONNECT와 `pg_monitor` 멤버십(통계 뷰와 설정)뿐이다. `public`·`obs`의 어떤 테이블·뷰·시퀀스·열에도 권한이 없고, CREATE와 임시 테이블도 없으며, 연결은 최대 3개, 세션은 읽기 전용이고 문장 제한은 10초다. `pg_monitor`에는 `pg_read_all_stats`가 들어 있어 이 역할은 `pg_stat_activity`에서 다른 세션의 구문 원문을 읽을 수 있다. 내보내기 쿼리는 이를 고르지 않으며, 비밀번호는 다른 역할 비밀번호처럼 다룬다. 스크립트는 테이블이 필요 없어 DB가 생긴 뒤 언제든 실행할 수 있다(스모크는 Flyway 뒤에 돌린다). `docker compose down -v`나 새 볼륨 뒤에는 다시 실행한다. ## 8. 헬스체크·종료·로그

- `api` probes (MON-01, 2026-11-13): the container healthcheck calls `/readyz` on the API port 8080 — the readiness group exposed there by `management.endpoint.health.probes.add-additional-paths=true`, so the probe passes through the same connector and threads as API requests (Spring Boot reference, "Kubernetes probes"); `/livez` is the liveness group. - 그레이스풀 셧다운(P0-24 실측: `docker compose stop api`가 SIGTERM을 Java(PID 1)에 전달 → 로그 "Commencing graceful shutdown … complete", 종료 코드 143, 강제 종료 없음. 처리 중 요청이 있는 상태의 종료는 M1-03 스모크가 시험한다 — 아래): Spring Boot 4.1.2·3.5.16 문서 모두 "내장 웹 서버에서 기본 켜짐"이다(2026-11-08 확인). 3.5 이상이면 정할 값은 대기 시간 `spring.lifecycle.timeout-per-shutdown-phase`(예 20s)뿐이고, 3.4 이하를 고르면 해당 판의 문서로 다시 확인한다. compose `stop_grace_period: 30s` > 20s.
- Shutdown time relation (M1-03, measured 2026-11-17 on the arm64 image, Docker Desktop): a client request time ≤ the Spring phase timeout `spring.lifecycle.timeout-per-shutdown-phase` 20 s < `stop_grace_period` 30 s. Tomcat stops serving new connections at once, a request in flight when `docker stop` arrives finishes (a 3 s wait on a table lock: 201, exit code 143, stop in about 4 s), and a request still running after 20 s is cut: the log shows "Graceful shutdown aborted with one or more requests still active" and the client gets no response. The line "Graceful shutdown complete" is also logged after that abort, so it alone proves nothing. The 10 s of margin up to `stop_grace_period` covers the JVM shutdown after the phase ends; with a margin of zero Docker would send SIGKILL (exit 137). Keep the limit of every call that holds a request (database and external calls) below 20 s. A start without `ANTLAB_DB_URL` under `prod` exits with code 1 in about 2 s and the log says `'url' must start with "jdbc"` (the unresolved placeholder reaches the pool; the variable name is not in the message). / 종료 시간 관계(M1-03, 2026-11-17 arm64 이미지·Docker Desktop에서 실측): 클라이언트 요청 시간 ≤ Spring 단계 시간 제한 `spring.lifecycle.timeout-per-shutdown-phase` 20초 < `stop_grace_period` 30초. Tomcat은 새 연결을 바로 받지 않고, `docker stop`이 올 때 처리 중이던 요청은 끝까지 처리된다(테이블 잠금에서 3초 대기: 201, 종료 코드 143, 정지 약 4초). 20초가 넘도록 끝나지 않는 요청은 끊기며 로그에 "Graceful shutdown aborted with one or more requests still active"가 남고 클라이언트는 응답을 받지 못한다. "Graceful shutdown complete" 줄은 그 중단 뒤에도 찍히므로 그것만으로는 아무것도 증명하지 못한다. `stop_grace_period`까지의 10초 여유는 단계가 끝난 뒤 JVM 종료를 위한 것이며, 여유가 없으면 Docker가 SIGKILL(종료 코드 137)을 보낸다. 요청을 붙잡는 모든 호출(DB·외부 호출)의 제한을 20초보다 짧게 둔다. `prod`에서 `ANTLAB_DB_URL` 없이 시작하면 약 2초 안에 종료 코드 1로 끝나고 로그는 `'url' must start with "jdbc"`다(치환되지 않은 자리표시자가 풀로 넘어가며, 메시지에 변수 이름은 없다).
- 로그: 모든 서비스는 **stdout/stderr에만**(파일 로그 금지). 운영 compose에 `logging: driver json-file, options max-size 10m, max-file 3`(json-file은 `max-size` 기본이 무제한이라 회전하지 않고, `max-file`은 `max-size`가 있어야 효과가 있다 — Docker 문서, 2026-11-08 확인). 키·토큰은 로그에서 `****`(tools/fetch 규칙 유지). Structured logs (MVP-20): the `prod` profile writes one ECS JSON object per line to stdout (`logging.structured.format.console=ecs`, `service.name=antlab-api`, banner off); `local` and tests stay plain text. Read with `docker compose logs --no-log-prefix api | jq -r .message`. / 구조화 로그(MVP-20): `prod` 프로필은 stdout에 줄마다 ECS JSON 객체 하나를 쓴다(`logging.structured.format.console=ecs`, `service.name=antlab-api`, 배너 끔). `local`과 시험은 일반 텍스트다. 읽을 때는 `docker compose logs --no-log-prefix api | jq -r .message`. 수집·대시보드(Loki 등)는 과함 — OPS 뒤 필요할 때.

### 9.2 설정 — 12-factor

- 설정은 **환경 변수가 이긴다.** Spring: `application.yml`에는 `${ANTLAB_…:기본값}` 자리표시자와 로컬 기본값만, 운영 값은 환경 변수(Spring relaxed binding: `SPRING_DATASOURCE_URL` 등)·configtree. `application-prod.yml`에 비밀값 금지(`.gitignore`가 `application-local.yml`·`application-secret.yml`을 이미 무시).
- 우리 변수 이름 접두사는 `ANTLAB_`(예: `ANTLAB_DB_PORT`, `ANTLAB_ENGINE_URL`, `ANTLAB_ENGINE_TOKEN`). 표준이 있는 것은 표준 이름 그대로 쓴다(`POSTGRES_*`, `SPRING_*`, `PG*`, `KIS_*`, `OPENROUTER_API_KEY`, `OLLAMA_BASE_URL`).
- 프로필은 SPRING_JPA §10의 `local`·`test`·`prod` 셋 그대로, 컨테이너에서는 `SPRING_PROFILES_ACTIVE=prod`.
- Python 엔진(M2) 기준: 설정은 `os.environ`이 먼저이고 `.env` 파일은 로컬 편의 대체만, `/healthz`, 비루트, 외부 네트워크 없음, DB는 읽기 전용 역할. `tools/fetch`는 `.env`를 명시 경로로만 읽고 `os.environ`을 바꾸지 않는다(`common.py`).
- Phase 0 API(Phase 1 JDBC 콘솔 앱은 건너뛰었다)의 접속 정보 역시 코드에 쓰지 않는다: `ANTLAB_DB_URL`(기본 `jdbc:postgresql://localhost:5432/antlab_api`), 사용자·비밀번호는 `ANTLAB_DB_USER`(기본 OS 사용자 `${USER}` — compose `POSTGRES_USER`와 같은 규칙)·`ANTLAB_DB_PASSWORD`(기본 빈 값)로 확정했다. `PGUSER`/`PGPASSWORD`는 libpq 변수라 JDBC 드라이버가 읽지 않으므로 Spring에는 쓰지 않는다. `prod`에서는 `ANTLAB_DB_URL`이 필수(기본값 없음)다(P0-24 — 빠뜨리면 기동에 실패해 localhost로 가지 않는다). 컨테이너의 `api`에는 compose가 `ANTLAB_DB_URL=jdbc:postgresql://db:5432/antlab_api`(서비스 이름과 컨테이너 포트)를 직접 준다. 호스트 `.env`의 URL이 그대로 넘어가지 않게 `env_file`로 `.env` 전체를 넘기지 않고 필요한 변수만 `environment`에 적는다. 설정 우선순위는 환경 변수 → configtree 파일이다 — 같은 속성(`spring.datasource.password`)을 `SPRING_DATASOURCE_PASSWORD`와 `/run/secrets` 파일로 함께 주지 않는다. The JWT key is the exception to "the environment wins": `ANTLAB_JWT_SECRET` is only a placeholder inside `application.yml`, so a `/run/secrets/antlab.auth.jwt-secret` file overrides it (measured in SEC-03); give the key one way only. / JWT 키는 "환경 변수가 이긴다"의 예외다: `ANTLAB_JWT_SECRET`은 `application.yml` 안의 자리표시자일 뿐이라 `/run/secrets/antlab.auth.jwt-secret` 파일이 덮어쓴다(SEC-03에서 측정). 키는 한 가지 방법으로만 준다. 로컬 compose `db`에 그대로 연결한다. ## 10. 호스팅

### 10.1 OCI Always Free 한도 (https://docs.oracle.com/en-us/iaas/Content/FreeTier/resourceref.htm, 2026-11-08 확인)

- VM.Standard.A1.Flex: 월 **1,500 OCPU 시간 · 9,000 GB 시간 = 2 OCPU · 12 GB 메모리** 상당. 이전에 널리 알려진 4 OCPU · 24 GB가 아니다. 블로그들은 2026-06에 절반으로 줄었다고 하나 공식 페이지에는 변경 시점 언급이 없다 — 시점은 **확인 필요**, 현재 값은 확인됨.
- 블록 볼륨: 홈 리전에서 부트 + 블록 합계 200 GB, 볼륨 백업 5개. 오브젝트 스토리지 20 GB. 아웃바운드 전송 월 10 TB.
- **유휴 회수:** "Idle Always Free compute instances may be reclaimed" — 7일 동안 CPU p95 < 20%, 네트워크 < 20%, 메모리 < 20%(A1만)이면 유휴. 사용자가 적은 게임 서버는 쉽게 이 조건에 든다. 종량제(Pay As You Go) 전환 시 무료 한도 안이면 과금 없이 회수가 멈춘다는 것은 2차 자료뿐 — **공식 확인 필요**(OPS 때).
- A1 용량 부족("Out of capacity")으로 생성이 안 되는 리전이 있다는 보고 — **확인 필요**.
